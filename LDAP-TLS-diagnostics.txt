Sippy LDAP connection investigation — 2026-11-26

Tested endpoint: cd-byod.ringcentral.com:636
DNS answer (local resolver and Google public DNS agreed):
  cd-byod.ringcentral.com -> cd-byod.geo.ringcentral.com -> 66.81.246.91

An independent Java TLS client was used, without Sippy or its LDAP SDK.
Server CA trust and hostname checks remained enabled. No LDAP password
or account credentials were needed or transmitted during these probes.

Results with no client certificate:
  TLS 1.3, SNI absent:   received fatal TLS alert certificate_required
  TLS 1.3, SNI present:  received fatal TLS alert certificate_required
  TLS 1.2, SNI absent:   received fatal TLS alert handshake_failure
  TLS 1.2, SNI present:  received fatal TLS alert handshake_failure

Both TLS 1.3 and TLS 1.2 exchanges contain a server CertificateRequest. The acceptable
issuer list includes Polycom Equipment, Cisco Manufacturing, Yealink
Equipment/Manufacturing, Snom, Mitel and RingCentral certificate authorities,
as well as several public roots.

The server presented a publicly trusted certificate for
  CN=cd-byod.ringcentral.com, O=RingCentral, Inc.
issued by
  CN=Thawte TLS RSA CA G1, O=DigiCert Inc, C=US.

The TLS alert is received before an LDAP bind can be processed. It therefore
does not establish whether the LDAP username or password is correct.

Interpretation (requires RingCentral confirmation):
The tested endpoint appears to enforce a client/device certificate policy.
Supported desk phones may already carry manufacturer-issued certificates,
which could explain instructions that only mention LDAP credentials. This
is a hypothesis; no claim is made about RingCentral's intended account policy
or other regional servers.
